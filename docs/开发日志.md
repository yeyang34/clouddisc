## 案例 1 · 编译通过 ≠ API 用对了

- **现象**：按 Yarn javadoc 实现 `AudioStream`（只看到 `getFormat()` 与 `getBuffer(int)`），编译报"未覆盖 `close()`"。
- **根因**：javadoc 的**成员列表不显示继承来的方法**；`AudioStream` 其实继承了 `Closeable`。
- **教训**：文档是二手信息，编译器和真实字节码才是一手。后面我干脆反编译了官方 jar。

## 案例 2 · 挂点找错了层级（1010/1011 到底在哪处理）

- **初判**：`ClientWorld#syncWorldEvent`（Yarn javadoc 里确实声明了它，拦截也确实生效）。
- **反编译后的真相**：真正的播放逻辑在 `LevelRenderer#levelEvent` → `playStreamingMusic`
  （Yarn：`WorldRenderer#processWorldEvent` → `#playSong`）；`ClientWorld.syncWorldEvent` 只是上游委托点。
- **影响**：在更上游拦截会连带丢掉 HUD 曲名与"鹦鹉跳舞"，已作为 v0.2 的改进项记录在案
  （设计文档 §2.4 给了可直接照抄的 `@Redirect` 写法）。

## 案例 3 · 不开游戏也能验证注入点

- **方法**：读构建产物里的 `clouddisc-refmap.json`。Loom 的注解处理器会把 `@Inject(method = "...")`
  的名字与描述符解析成混淆名——**能在混淆表里找到，就会解析成 `class_XXX;method_YYYY(...)`**；
  找不到就留原样。
- **结果**：
  - `syncWorldEvent` → `class_638;method_8444(Lclass_1657;ILclass_2338;I)V`
  - `loadStreamed` → `class_4237;method_19744(Lclass_2960;Z)Ljava/util/concurrent/CompletableFuture;`
  - `addMessage(Text)` → `class_338;method_1812(Lclass_2561;)V`
  - `addMessage(Text, MessageSignatureData, MessageIndicator)` → `class_338;method_44811(...)`
- **意义**：这是"方法名写错"这类错误的静态证据，比等运行时崩掉快得多。

## 案例 4 · 网易云的链接分三种，只有一种是音频

实测（curl，本机）：

| 链接形态 | 实测结果 |
|---|---|
| `music.163.com/song?id=186016` | `200 + text/html`，137 KB —— **网页，不是音频** |
| `music.163.com/song/media/outer/url?id=X.mp3` | 看歌而定（见下） |
| `163cn.tv/xxxx` | 跳网页，解析不出音频 |

外链抽样 8 首：**3 首返回 `audio/mpeg`**（302 跳到 `m80x.music.126.net/...mp3`，3–5 MB），
**5 首 302 到 `https://music.163.com/404`**，返回 107 KB 的 HTML（含《晴天》）。
UA / Referer 与结果无关（三种 UA 一致）。

**结论**：只播"匿名就能播的内容"；VIP 歌交给玩家自己的解析服务。

## 案例 5 · curl 能过、Java 不能过

- **现象**：curl 拿到 `audio/mpeg`，mod 里却停在 302 上。
- **根因**：Java `HttpClient.Redirect.NORMAL` 的语义是"**除 https→http 之外**都跟随"，
  而外链的 302 目标正是 http 的 CDN。
- **修法**：`Redirect.ALWAYS`；并加 `Content-Type` 校验——把 VIP 那 107 KB 的 HTML
  变成一条明确报错，而不是语焉不详的"解码失败"。

## 案例 6 · 下载成功了却认不出格式（`.bin` 事件）

- **现象**：缓存里出现 `f52790bb.bin`（5093 KB，音频明明已经下好），随后报"已实现 OGG/WAV/MP3"。
- **根因**：用 `URI.getPath()` 推扩展名，而 **`getPath()` 不含查询串**；
  网易云把 `.mp3` 放在了 `?id=1330348068.mp3` 里。
- **修法**：改为**按文件头魔数识别**（`OggS` / `RIFF..WAVE` / `ID3` / `0xFF 0xEx` / `fLaC`），
  从此不依赖文件名、重定向、Content-Type。

## 案例 7 · 全静音（量纲混用）

- **现象**：节拍器与网易云**同时**完全没声音，日志里峰值打成 `32230.428`。
- **定位**：下混时我只除以声道数（缓冲区里是 ±32768 的**原始 16 位幅度**），
  而软限幅是按"±1.0 为满刻度"写的 → `if (abs > 0.95)` 对 ±30000 永远成立
  → 每个样本都被压成 ±0.95，写回 16 位取整后就是 **±1 LSB ≈ 静音**。
- **修法**：统一下混 / 限幅 / 写回为归一化空间（下混 ÷32768，写回 ×32767）。
- **留下的东西**：输出峰值诊断日志——**这个数字本身就把量纲错误暴露了**（归一化音频不可能出现 32230）。

## 案例 8 · 日志骗了我们 4 秒（进度口径）

- **现象**：两台实例的"差"稳定显示 `-4000ms`，看起来像差了 4 秒。
- **定位**：心跳报的是 `playedMs()`（**已交给 MC 的字节数**），而 `attachBufferStream`
  会立刻 `pumpBuffers(4)`——MC 的 OpenAL 队列一开始就压了约 4 秒。
  而对比用的"本机位置"是游戏刻推算的，**两个量纲不同**。
  证据就在同一份日志里：**"起播 1 秒后已消费 3919ms"**——一秒内不可能真播掉 3.9 秒音频。
- **修法**：心跳改报"内容位置"（开声刻 + 游戏刻推算）。按同一口径重算旧日志，真实偏差约 100 ms。

## 案例 9 · "走步 / 被强行拽回去"（周期性 seek）

- **现象**：跟随方听感像被人拽着走。
- **根因**：因为案例 8 的口径错误，比对结果**永远差几秒** → 每秒触发一次 seek
  → 每次 seek 都清空环形缓冲重填 → 音乐被切成一段一段。
- **修法**：参考原版做法（`LevelRenderer.playStreamingMusic` 只 `play()` 一次、全程不纠偏），
  改为"预取完成 → 广播统一开始刻 → 各端到点零延迟开声"，**删除周期性纠偏**。

## 案例 10 · 中途加入卡 10 秒然后播错位置（seek 死锁）

- **现象**：`LATE 35850ms` 之后隔了 11 秒才 `PLAY-START`，随后差值为 `-9650ms`。
- **定位**：解码线程灌满环形缓冲后**阻塞在 `write()`**；缓冲腾空要靠 MC 消费，
  而 MC 要等我们 `play()`；seek 又必须在解码线程的循环顶部执行 → 互相等，
  `requestSeekBlocking` 超时 10 秒（正好是那 11 秒空档），接着播出缓冲区里那份"开头"的数据。
- **修法**：请求 seek 前先 `ring.clear()` 放行阻塞中的写入；超时改成明确 ERROR。

## 案例 11 · 发起方"还没准备好就回话"（-28440 刻）

- **现象**：对方算出 `startTick - sentTick = -28440`，触发兜底 → **提前约 2 秒**开始（`DRIFT 1800ms`）。
- **定位**：放碟后会先解析 + 预取，这段时间会话已在表里但 `localStartTick` 仍是 `0`；
  此时回答了对方的追问，于是发出去的 `startTick = 0`。
  两个观测值（`-28440 刻` 与 `1800ms`）同时对上，排除其他可能。
- **修法**：未排定开始刻就不应答；接收方忽略没有有效调度的消息。

## 案例 12 · 重进服完全不播放（跨客户端刻换算）

- **现象**：B 退出重进后**一点声音都没有**。
- **定位**：刚进服的客户端 `world.getTime()` 与房主能差**几万刻**（日志里出现过 `-28440 刻`，
  更早还有 `LATE 1000900ms`）→ 算出的位置**越过文件末尾** → 管道立刻读到结尾 → MC 收到空缓冲。
- **修法**：重进服 / 中途加入一律用对方给出的**内容位置**定位；再加"位置超过 60 分钟就明确放弃并报错"。

## 案例 13 · 双开时对方听到原版（端口被 SO_REUSEADDR 吃掉）

- **现象**：双开测试时，跟随方一直放原版唱片。
- **定位**：Windows 允许两个进程用 `SO_REUSEADDR` 绑**同一个 UDP 端口**，
  而单播数据只会交给其中一个 socket → 发起方发出的同步消息另一个实例收不到。
- **修法**：数据端口**不设** `SO_REUSEADDR`，绑不上就往后试（25566 → 25567）；
  发现改为固定组播组，与端口无关。

## 案例 14 · 我的误判：把"计数"当证据

- **现象**：两个实例的日志都显示 `udp=2`（两实例应该是 1 个对端），我据此猜测"有第三个实例在跑"。
- **真相**：把"发现同伴"那几行的**地址**打出来一看——同一台 B 被记了两次
  （一次走局域网 IP `192.168.2.13:25567`、一次走 `127.0.0.1:25567`）。
- **修法**：presence 包带实例 id，按 id 去重。
- **教训**：**先看原始地址再下结论**。我把计数当成了证据，白花了一轮。

## 案例 15 · "文件没问题，是我错了"（独立探针）

- **背景**：日志说某个缓存 mp3"输出峰值 0.000"，但 curl 明明能下到 5 MB 音频。
- **做法**：写了个**脱离游戏**的探针（`Mp3Probe`，同一套 JLayer 调用），把三个缓存文件全解一遍：
  三个文件都 `peak=1.0000`、非零样本 97–99% → 证明文件与解码器都正常。
- **价值**：当"现象"和"代码"都说服不了自己的时候，**写个最小独立验证最快**。
  （那次真正的问题是案例 7 的量纲错误。）

## 案例 16 · 一个注解让客户端启动就崩（`@Environment` 用在了 main 入口点上）

- **现象**：装上 0.4.0 后游戏**启动即崩**，崩溃报告写着：
  ```
  Could not execute entrypoint stage 'main' … at 'dev.clouddisc.server.CloudDiscServer'
  Caused by: java.lang.RuntimeException: Cannot load class … in environment type CLIENT
    at net.fabricmc.loader.impl.transformer.FabricTransformer.transform
  ```
- **根因**：我在服务端入口类上加了 `@Environment(EnvType.SERVER)`。
  这个注解的语义**不是**"跳过调用"，而是 **"环境不匹配时让这个类无法加载"**（Fabric 会改写字节码摘掉标注元素）；
  而 **`main` 入口点在物理客户端上也会被执行** → 客户端去加载入口点时被拦下 → 启动崩溃。
- **修法**：类上**不加注解**，在 `onInitialize()` 里做运行时判断（`FabricLoader.getInstance().getEnvironmentType() != EnvType.SERVER` 就直接 return）。
- **精确的规则**：
  - `main` 入口点跑在两端 → 类必须两端都能加载 → **不能用 `@Environment`**，要运行时判断；
  - `client` 入口点不受影响（专用服务端根本不会调用它），所以客户端 mod 照常标 `@Environment(CLIENT)`；
  - 客户端 Mixin 配置写在 `environment: client` 里，服务端连配置都不会加载，同样安全。
- **教训**：这条在调研阶段就被提醒过（"Fabric-loader will remove the annotated element in a mismatched environment"），
  我把它理解成了"安全地跳过"，实际是"直接不可加载"。**注解的语义要看它到底做什么，别按直觉套**。
- **为什么这次没提前拦住**：这类错误只在真实启动时暴露，而本机没有可运行的游戏环境。
  事后我加了一条静态检查思路：入口点类一律禁止 `@Environment`（见方法论第 7 条）。

## 案例 17 · "有时候会卡出原版的音乐"（两条音轨同时响）

- **现象**：**偶发**。放碟后有时能同时听到原版唱片声和我们的音乐。
- **定位**：同一种错误出现在两条路径上 —— **原版那条声音响了之后没人把它收回来**：
  1. `onWorldEvent` 的"还没发现同伴"分支会 `PASS`（不拦 1010），原版正常开声；
     而同伴的 `PLAY` 可能在**之后**才到 → 我们接上 → 两条同时响。
     **"有时候"就是这么来的**：它取决于组播发现与消息到达的先后顺序。
  2. 等待答复超时后的"回落原版"用的是 `world.playSound(...)` —— 这是**野生声音**，
     没进原版 `playingSongs` 记账表，**谁都停不掉它**；等我们真接上时同样变成两条。
- **修法**：
  - 回落改走**原版入口** `WorldRenderer#playSong(disc.getSound(), pos)`
    （顺带白拿 HUD 曲名与鹦鹉跳舞）；
  - `playNow` 里**开声前先 `playSong(null, pos)`**，把该唱片机上原版那条停掉 —— 两种来源一次覆盖。
- **教训**：凡是"我们可能让位给原版"的设计，都必须回答**"接管时怎么把原版那条收回来"**。
  **让位不是问题，让位后没人收摊才是问题。**
- **顺带学到的**：`WorldRenderer#playSong` 是 public 的，所以"停掉原版那条唱片声"不需要任何 Mixin
  —— 这是本项目第二次靠"原版方法恰好是 public"避开注入风险（第一次是 §2.4 的 HUD 曲名）。

## 案例 18 · "退出世界再回来有时不播放"（一个日志行暴露的偶现 bug）

- **现象**：偶现 —— 退出世界重进后，有时接不上、直接不播放；再试几次又好使。
- **线索**：日志里 `发现同伴 127.0.0.1（数据端口 25568）` 与
  `发现同伴 192.168.2.13（数据端口 25568）` **每 2 秒重复一次**。
  而这行代码只在"新同伴"时打一次 —— 说明对端条目在反复消失。
- **根因（同一处设计的两面）**：
  1. **判断与发送共用一个超时**。判断"有没有对端"必须严格（10 秒），
     但发送也用它就错了：对端重启后数据端口会变（实测 25566 → **25568**），
     旧地址在严格超时内还"有效"，消息发到旧端口就丢了；广播偶尔丢包也会让地址表瞬间变空。
     → 结果：重进后那句关键的"谁在放什么"询问**发不出去** → 没人回答 → 没有会话 → 静音。
  2. **按地址登记 + "删掉旧地址"**。同一个同伴的广播会**交替**从局域网 IP 与 `127.0.0.1`
     进来（多网卡/组播回环），于是每次都把另一条删掉 → 每 2 秒"发现"一次，
     期间对端表还会短暂指向过期地址。
- **修法**：
  - **判断用严格超时，发送用宽松记忆**：发往"当前有效对端 ∪ 最近 60 秒见过的地址"；
  - 对端改按**实例 id** 登记（一个同伴 = 一条记录，不再自我打架）；
  - 进服后的主动询问 3 → 5 次，并在"对端出现 + 本机无会话 + 进服 60 秒内"时立刻补问。
- **教训**：**"我知道谁在"和"我要发给谁"是两个不同的问题**，用同一个数据结构 + 同一个超时
  去回答，就会在"对端刚重启/广播刚丢一包"这类缝隙里失败 —— 偏偏这些缝隙正是偶现 bug 的藏身处。
  另一个教训：**日志里"本该只出现一次的行"开始重复，就是最好的线索**（本案例完全靠它定位）。

## 方法论小结

1. **先看一手**：javadoc 会漏继承方法；要结论就反编译字节码。
2. **静态能验的别等运行时**：refmap 能提前证明注入点对不对。
3. **让日志说人话**：`请求位置 vs 实际位置`、`输出峰值`、`起播 1 秒后已消费多少`
   —— 这几个数出现过一次"假警报"，但正是它们把范围从"网络侧"拉到"音频层"。
4. **量纲和口径要写进注释**：本项目两次最贵的错误都是"两个量纲混用"（案例 7、案例 8）。
5. **计数不是证据**：`udp=2` 让我误判过一次，地址才是证据（案例 14）。
6. **独立探针**：能脱离宿主跑的最小验证，性价比最高（案例 15）。
7. **注解看语义，别看直觉**：`@Environment` 不是"跳过调用"而是"让类无法加载"，
   用错在入口点上就是启动崩溃（案例 16）。入口点类一律禁止 `@Environment`。
