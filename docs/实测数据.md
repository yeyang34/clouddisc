## 1. 同步精度

**环境**：同一台电脑开两个游戏版本目录（version isolation），进同一个局域网世界（一个开房、另一个 `127.0.0.1` 连入）。
**方法**：发起方每秒广播一次"此刻的内容位置"，跟随方与自己的位置比对（同一量纲，见开发日志案例 8）。

| 时间 | 发起方位置 | 本机位置 | 差值 |
|---|---|---|---|
| 22:44:36 | 100 ms | 50 ms | **-50 ms** |
| 22:44:46 | 10150 | 10100 | **-50 ms** |
| 22:44:56 | 20200 | 20150 | **-50 ms** |
| 22:45:06 | 30250 | 30200 | **-50 ms** |
| 22:45:16 | 40300 | 40250 | **-50 ms** |
| 22:45:26 | 50350 | 50300 | **-50 ms** |
| 22:45:36 | 60400 | 60350 | **-50 ms** |
| 22:45:46 | 70450 | 70400 | **-50 ms** |
| 22:45:56 | 80500 | 80450 | **-50 ms** |
| 22:46:06 | 90550 | 90500 | **-50 ms** |

**结论**：

- 偏差恒为 **50 ms**，且这正是"一个游戏刻"的长度 → 说明误差来自**刻的量化精度**，不是逻辑缺陷；
- 90 秒窗口内**完全不增长**，即无累积漂移；
- 另一次较早的测试里，两端各自推算的内容位置为 **46.0 s 与 46.1 s**（差约 100 ms），与上表互相印证。

> 已知残余误差还有一项：两台机器声卡各自的输出缓冲延迟（通常 20–80 ms），
> 这是**听感上的常量偏移**，无法用软件消除，也不随时间长。

## 2. 中途加入 / 从 64 格外走近

**成功的一次**（B 在 A 已经放了 45 秒之后才接上）：

```
B  已加入世界，将主动询问一轮『谁在放什么』
B  收到未知坐标的心跳，主动询问该处会话 @ {199,64,141}
B  收到 A: startTick=… sentTick=… posMs=45150  本机刻=…
B  按对方的内容位置定位: 45150ms（重进服/中途加入）
B  起播已过开始刻（晚了约 45150ms）：一次性 seek 对齐后再开声
B  已开始播放: 网易云 #1297493058（请求位置 45150ms / 实际 45150ms）
```

**结论**：从第 **45.15 秒**接上，不从头、不静默。日志同时打出"请求位置 / 实际位置"两个数，
它们一致就说明 seek 真的生效了（这一行是后来加的，之前正是它缺失导致问题难查）。

**（修复前）同一路径的失败样本**，留作对照：

```
LATE late=35850ms
…… 11 秒空档 ……
PLAY-START from=35850ms   ← 请求 35850
DRIFT    diff=-9650ms     ← 实际差了近 10 秒（seek 超时，播的是缓冲里的旧位置）
```

## 3. 网易云可用性抽样（8 首，2026-10 实测）

请求形态：`https://music.163.com/song/media/outer/url?id=<id>.mp3`（跟随重定向）

| 歌曲 id | HTTP | Content-Type | 大小 | 可播 |
|---|---|---|---|---|
| 1330348068 | 200 | `audio/mpeg` | 5 214 920 B | ✅ |
| 5169250 | 200 | `audio/mpeg` | 5 616 996 B | ✅ |
| 569213220 | 200 | `audio/mpeg` | 3 320 729 B | ✅ |
| 186016（晴天） | 200 | `text/html` | 107 191 B（302 到 `/404`） | ❌ |
| 347230 | 200 | `text/html` | 107 191 B | ❌ |
| 1901371647 | 200 | `text/html` | 107 191 B | ❌ |
| 28949444 | 200 | `text/html` | 107 191 B | ❌ |
| 26217052 | 200 | `text/html` | 107 191 B | ❌ |

**结论**：

- 可播的 3 首都是 **302 跳到 `http://m80x.music.126.net/...mp3`**（注意目标是 **http**，见开发日志案例 5）；
- 不可播的 5 首统一跳到 `https://music.163.com/404`，返回 **107 KB 的 HTML**（不是 4xx 状态码！），
  所以必须按 `Content-Type` 判定，不能只看状态码；
- **UA / Referer 与结果无关**（三种 UA 结果一致）；
- 另一形态 `music.163.com/song?id=186016` 返回 **137 KB 的 HTML**（歌曲网页，不是音频）。

## 4. 音频链路指标

| 指标 | 实测值 | 说明 |
|---|---|---|
| 输出峰值 | **0.810 / 0.984**（未削顶） | 归一化空间；>1.0 才削顶 |
| MC 消费进度 | 起播 1 秒 **3919 ms**；5 秒 **7913 ms**；90 秒 **90550 ms** | 持续消费、无欠载 |
| 环形缓冲积压 | 稳定 **5461 ms** | 解码始终跑在前面 |
| 预缓冲 | 2136 / 3065 / 3343 / 3622 / 4272 / 5461 ms | 视曲目而定 |
| 放碟 → 出声 | 约 **2 秒**（预取 <1 秒时）；下载慢时顺延 | = 统一开始刻提前量 40 刻 |


## 8. 元数据接口实测（本机直连，0.6.1）

**目的**：确认"物品只存 id、播放时显示真名"这条路真的能拿到歌名。

请求形态：`https://music.163.com/api/song/detail/?id=<id>&ids=[<id>]`，带 `UA` + `Referer: music.163.com`，**不带任何账号/cookie**。

| 歌曲 id | HTTP | 歌名 | 歌手 | 专辑 |
|---|---|---|---|---|
| 1330348068 | 200 | 起风了 | 冯沁苑(买辣椒也用券) | 起风了 |
| 5169250 | 200 | Polynesia (Remix) | Mikron | I Love Disco Diamonds Collection Vol. 44 |
| 569213220 | 200 | 像我这样的人 | 毛不易 | 平凡的一天 |

**同时测出的两个坑（已修）**：

| 发现 | 影响 | 处理 |
|---|---|---|
| 歌曲网页的 `<title>` **是空的** | 原先设计的"网页 `<title>` 兜底"是**无效代码** | 改读分享标签 `og:title`（实测有值，如 `og:title content="起风了"`） |
| `/api/song/detail?ids=[id]`（不带 `id=`）**也能用** | 多一条可用路径 | 加为第二级兜底 |

**结论**：三级兜底（主接口 → 备用参数形态 → `og:title`）全部实测过；
三级都失败时回退到备注或 `网易云 #id`，**不影响播放**。
