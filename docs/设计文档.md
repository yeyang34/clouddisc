# 歪歪网易云唱片 CloudDisc · 设计文档

> **歪歪网易云唱片mod——忠于原版，高于原版**

> Minecraft Java Edition **1.20.1** / **Fabric** / **纯客户端（client-only）**
> 目标：让"被铁砧改过名的唱片"在唱片机里播放网络音乐，并且**真正替换**唱片机发出的声音，同时让所有装了本 Mod 的玩家听到**同一进度**。

---

## 0. 一页速览

| 问题 | 结论 |
|---|---|
| 客户端能不能读到唱片机里那张唱片的改名/NBT？ | **不能。** `JukeboxBlockEntity` 既不重写 `getUpdatePacket` 也不重写 `getUpdateTag`，服务端只通过世界事件 1010 发一个**物品数字 ID**。 |
| 那怎么"真正替换"唱片机声音？ | 让 MC 自己的音频引擎播放我们的 PCM：合成一个 `Sound`（`stream=true`）+ 一个自己的 `AudioStream`，在 `SoundLoader#loadStreamed`（= Mojang `SoundBufferLibrary#getStream`）处注入。位置衰减、RECORDS 音量、暂停、停止全部沿用原版。 |
| 曲目身份怎么在玩家之间传？ | 曲目信息编码进**唱片名字**（铁砧改名是服务端权威动作，物品走到哪名字跟到哪）；播放瞬间由**发起方**把解析结果（含 URL）通过玩家间通道广播。 |
| 没有服务端 mod 怎么玩家间通信？ | 主通道 **UDP 点对点**（局域网广播发现）；聊天消息做**信令/兜底**。已用**反编译源码**确认：原版服务端 `ServerGamePacketListenerImpl#handleCustomPayload` 是**空方法**，什么都不转发；`minecraft:brand` 在 1.20.1 服务端也没有任何代码读取。 |
| 进度怎么同步？ | 发起方广播"统一开始刻（含预缓冲 lead）"，各端预缓冲后在**同一个服务器刻**开始；之后心跳纠偏，偏差 >150 ms 时 seek 硬对齐。 |
| 网易云怎么办？ | 本 Mod **不内置**任何第三方接口、不内置任何人的 cookie、**不支持解密受保护格式**。网易云只是一条"你自己有权限的接口地址"的可插拔 provider，默认关闭。合规默认音源 = 本地文件 / 自建 Subsonic·Navidrome。 |
| 已经做了多少？ | **可编译骨架已通过 `gradle build`**（JDK 17 + Gradle 8.8 + Loom 1.6.12，产出 `clouddisc-0.1.0.jar`）：音频管线、播放控制、同步协议、UDP 通道、两个 Mixin、音源 provider。OGG 解码已实现；MP3/FLAC/AAC 见 §5。 |
| 没做/最需要实测的是什么？ | ① 音频注入与 `getBuffer` 语义要在 `runClient` 里实跑（§12 清单）；② 聊天通道的**入站 hook** 刻意留空（§7.3）；③ 铁砧名→曲目的解析链需要你自己接一个合法音源（§8）。 |

**证据等级说明（诚实标注）**：本文的类名/方法名/版本号全部来自一手来源：Yarn 1.20.1 javadoc、Fabric meta/Maven、LWJGL javadoc、Modrinth API；而"调用链/线程/缓存/限流阈值"这类**行为**结论，来自对 **1.20.1 官方 client.jar 的 CFR 反编译源码**逐行阅读（混淆源码已留在工作区 `mc1201-decompiled/`，含 `MAPPING-NOTES.md` 对照表与行号，你可以直接打开核对）。凡未实测的，都写了"待实测"；§15 单列待核实清单。

## 1. 需求拆解与硬约束

你的三条需求，翻译成技术约束：

**R1 纯客户端、不依赖服务器，但装了 Mod 的玩家之间同步**
- 约束 A：不能要求服务端装任何东西 → 不能用 Fabric/Forge 的服务端自定义包（`ServerPlayNetworking` 必须服务端也装）。
- 约束 B：玩家的客户端拿不到服务端权威数据（除了原版同步下来的世界状态）。
- 推论：**玩家间需要一个绕过 MC 协议的旁路通道**，且这个通道在"原版服务器 + 玩家各自在家"的拓扑下也要能通。

**R2 改名即点歌，且必须替换唱片机原声（不是外挂播放）**
- 约束 C：不能用额外的音频库自己开声卡（那会绕过游戏音量、暂停、失焦静音、空间衰减，就是你说的"外挂"）。
- 约束 D：必须走 MC 的 `SoundSystem` → OpenAL 链路，只是把喂进去的 PCM 换成自己的。
- 约束 E："改名"这个动作必须是**服务端认可**的，否则换个玩家/换个容器就丢了 → 只能借铁砧（服务端执行改名）。

**R3 所有装了 Mod 的玩家进度同步**
- 约束 F：需要一个共同时间基准；MC 客户端能拿到的共同基准只有 `level.getGameTime()`（服务器刻，约 20 Hz 同步）。
- 约束 G：音乐进度误差要压到人耳可接受范围（经验上 <50 ms 就很自然；<150 ms 基本听不出"接不上"）。

## 2. 四个关键判断（以及核实依据）

### 2.1 判断一：客户端**读不到**唱片机里的唱片 —— 所以同步层不是可选项

核实（Yarn 1.20.1 javadoc）：

- `JukeboxBlockEntity` 声明的方法里**没有** `getUpdatePacket` / `getUpdateTag`；整个类页面里也**没有**出现 `ClientboundBlockEntityDataPacket`。
  依据：[JukeboxBlockEntity (yarn 1.20.1+build.10)](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/block/entity/JukeboxBlockEntity.html)
- 它的字段是 `inventory` / `isPlaying` / `recordStartTick` / `tickCount` / `ticksThisSecond`，全部是服务端侧状态。
- 客户端能拿到的只有世界事件 1010 的 `data`，语义是 `Item.getRawId(唱片物品)` —— **只有物品 ID，没有 NBT、没有改名**。
- 唱片在唱片机里也不是靠 BlockEntityRenderer 画的（原版没有 JukeboxRenderer），而是靠 blockstate `has_record` 换模型，所以客户端连"看一眼物品"的机会都没有。

**结论**：任何"客户端各自从唱片机读曲目"的方案都不成立。曲目身份必须**另外传**。
这反过来是好事：R2 和 R3 用的是同一套机制（把"哪个唱片机在放什么"广播出去），设计更收敛。

**一个精确的补充（反编译源码级）**：`JukeboxBlockEntity` 的 NBT 键是 `RecordItem` / `IsPlaying` / `RecordStartTick` / `TickCount`，只有 `readNbt`/`writeNbt`，没有任何 update-packet。但 `toInitialChunkDataNbt()` 的默认实现就是"完整 NBT"，所以**如果某个玩家是在唱片已经在机子里之后才加载这个区块**，他的客户端副本里**可能**带着那张唱片的改名。
→ 这给了一条零网络的旁路：`world.getBlockEntity(pos) instanceof JukeboxBlockEntity` → `getStack(0).getName()`。
→ 但它**不覆盖主场景**（你在我旁边放碟时，我的区块数据早就发过了，客户端副本不会更新）。所以它是 v0.2 的加分项（让"漏斗塞碟"和"后来才加载区块的人"也能知道曲目），不是主路径。

另外两个必须记住的常量：1010 的 `data = Item.getId(item)`；**1011 的 `data = 0`**（不是物品 ID）。所以 WIP 时不要拿 1011 的 data 去反查物品。

### 2.2 判断二：替换原版声音的正确挂点是 `SoundLoader#loadStreamed`

先纠正一个常见误解：**1.20.1 的 `SoundInstance` 没有 `getStream()`，也没有 `resolve(SoundManager)`**。

核实（Yarn 1.20.1 javadoc）：

- `SoundInstance` 的全部方法：`getId()`、`getSoundSet(SoundManager)`（= Mojang 的 `resolve`）、`getSound()`、`getCategory()`、`isRepeatable()`、`isRelative()`、`getRepeatDelay()`、`getVolume()`、`getPitch()`、`getX/Y/Z()`、`getAttenuationType()`，外加默认方法 `shouldAlwaysPlay()`、`canPlay()`。
  依据：[SoundInstance](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/client/sound/SoundInstance.html)
- 真正取流的是 `SoundLoader#loadStreamed(Identifier, boolean) → CompletableFuture<AudioStream>`。
  依据：[SoundLoader](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/client/sound/SoundLoader.html)
- `SoundLoader` 就是 Mojang 的 `SoundBufferLibrary`（Yarn 改名）。它同时有 `loadStatic(Identifier)`。
- `Sound` 的构造器可直接 new：
  `Sound(String id, FloatSupplier volume, FloatSupplier pitch, int weight, Sound.RegistrationType type, boolean stream, boolean preload, int attenuation)`，
  `Sound.RegistrationType` = `{FILE, SOUND_EVENT}`，`isStreamed()` 即等于 `stream`。
  依据：[Sound](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/client/sound/Sound.html)、[Sound.RegistrationType](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/client/sound/Sound.RegistrationType.html)
- `WeightedSoundSet(Identifier, String)` 构造器 public、`add(SoundContainer<Sound>)` public，且 `Sound implements SoundContainer<Sound>` → 可以**绕开 `sounds.json` 注册**。
  依据：[WeightedSoundSet](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/client/sound/WeightedSoundSet.html)
- `AudioStream` 只有两个方法 `getFormat()` / `getBuffer(int) throws IOException`，并继承 `Closeable`。**返回空缓冲 = 流结束。**
  依据：[AudioStream](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/client/sound/AudioStream.html)、[OggAudioStream](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/client/sound/OggAudioStream.html)
- `SoundManager` 有 `play(SoundInstance)`、`play(SoundInstance, int delay)`、`stop(SoundInstance)`、`stopSounds(Identifier, SoundCategory)`。
  依据：[SoundManager](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/client/sound/SoundManager.html)、[SoundSystem](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/client/sound/SoundSystem.html)

**结论（替换方案）**：

1. 自定义 `SoundInstance`（本项目 `CloudDiscSoundInstance`）：
   - `getSoundSet(mgr)` 返回一个只含我们自定义 `Sound` 的 `WeightedSoundSet`；
   - 该 `Sound` 用 `RegistrationType.FILE` + `stream = true`，`id` 用**每次会话唯一**的 `clouddisc:stream/<n>`；
   - `getCategory()` = `SoundCategory.RECORDS`，`getAttenuationType()` = `LINEAR`，`getX/Y/Z` = 唱片机中心。
2. 自定义 `AudioStream`（本项目 `PcmAudioStream`）从环形缓冲取 PCM；
3. Mixin `SoundLoader#loadStreamed`：如果拿到的 `Identifier` 是我们注册过的那条流，直接 `setReturnValue(CompletableFuture.completedFuture(stream))`。

这样声音**就是 MC 的一条普通流式声音**：OpenAL source、3D 衰减、RECORDS 音量滑块、暂停/失焦、`stop()` 全部照旧。这就是"替换"而不是"外挂"的分界线。

> 排序上的一个坑：`Sound#getLocation()` 会把 `RegistrationType.FILE` 的 id 做前缀/后缀变换（形如 `clouddisc:sounds/stream/7.ogg`）。所以注册表匹配**不能硬编码**，本项目用"命名空间 + 路径中含 `stream/`"做归一化（`StreamRegistry.normalize`），不依赖具体拼接规则。
> 另一个坑：`Sound` 构造器内部会 `new Identifier(id)`，**会校验字符**（只允许小写 `a-z0-9/._-`）。用 `clouddisc:stream/<uuid 或计数器>` 是安全的，大写或空格会直接抛异常。

**反编译源码补充确认的三件事（都在 `mc1201-decompiled/` 里可查）**：

1. **调用链确实如此**：`SoundSystem.play` 里是
   `soundBuffers.getStream(sound.getLocation(), shouldRepeatInstantly).thenAccept(stream -> handle.execute(ch -> { ch.attachBufferStream(stream); ch.play(); }))`。
   注意第二个布尔参数是 **`shouldRepeatInstantly`（= `isLooping() && getRepeatDelay() <= 0`）**，不是 `isLooping()` 本身；本项目 `isRepeatable()` 返回 false，所以传进去是 false。传的是 **`Sound.getLocation()`**，不是 `SoundInstance.getId()`。
2. **`getStream` 完全没有缓存**：`SoundLoader` 只有一个 `Map<Identifier, CompletableFuture<...>>`，**只服务静态 buffer**（`loadStatic` 走 `computeIfAbsent`）。→ 用"每次会话唯一"的假 id 既不污染缓存也不泄漏；反过来，**hook 必须 `cancellable` 在 HEAD 直接返回自己的 future**，否则 vanilla 会真去 `resourceProvider.open(我们的假 id)` 并让 future 以异常完成。
3. **线程**：`getStream` 在 **Util 主工作线程**执行（所以 HTTP 拉取不能在里面同步等，要自己开线程并返回 future）；`getBuffer(int)` 在 **SoundExecutor 声音专用线程**执行 → **绝不能阻塞、绝不能抛**（抛 `IOException` 只会记一条错误日志然后彻底停止 pump，声音就悄悄没了；返回 `null` 才是安全跳过）。`SoundManager.play` 内部有 `createHandle(...).join()`，所以它会短暂阻塞调用它的线程 —— 别在渲染热路径里做重活。
   依据：`mc1201-decompiled/fyz.java`（SoundSystem，L296-388）、`fyy.java`（SoundLoader，L24-50）、`ege.java`（Source/Channel，L135-166）。

> ⚠️ **一个很容易踩的坑**：RECORDS 音量（或主音量）为 0 时，`SoundSystem.play` **会在调用 `getStream` 之前就 return**。也就是说"玩家把唱片机音量调到 0"这件事会**让我们的流式下载根本不启动**；之后他再调大音量也不会自动重播（除非重新触发 1010 或我们自己做重试）。本项目把"拉流/解码"放在 `getStream` **之前**（在 `prepareAsync` 里就下载+解码+seek 好，`getStream` 只是把已经准备好的环形缓冲包成 `AudioStream`），因此**天然规避**了这个坑。这是本项目架构上比较关键的一个选择。

### 2.3 判断三："名字即协议" —— 用铁砧改名当身份载体

为什么不能把曲目写进 NBT：**纯客户端 Mod 无法写服务端权威 NBT**。你在自己客户端给物品加的 NBT，服务端不认，进箱子/换玩家就没了。

而铁砧改名是**服务端执行**的：`display.Name` 会跟着物品一路走（掉落物、箱子、跨玩家、跨维度）。所以：

```
唱片名字 = "@<provider>:<trackId>"     例：@local:晴天.ogg   @netease:186016
```
- 前缀（默认 `@`）用来**避免误伤**普通改名唱片；
- 原版铁砧输入框上限 50 字符，所以 trackId 必须短（这正是"用短 key + 发起方解析"的原因）；
- 同一个名字在任何玩家客户端上含义一致**不需要**任何额外同步 —— 但"此刻哪台唱片机在放它"必须同步（见 §2.1）。

**由此得到一个很关键的简化**：真正需要联网的只有"发起方解析短 key → 真实 URL"这一步，而且**只有发起方需要配置音源**（§8）。

### 2.4 判断四：世界事件 1010/1011 的**实际处理位置**（决定 Mixin 挂点）

这一条是反编译源码才看清的，也是本项目里**唯一一处"能用但不够原版"的取舍**，所以单独讲清楚。

真实的客户端处理链（Yarn 名 / Mojang 名）：

```
ClientboundLevelEventPacket
   └─ ClientPlayNetworkHandler#onWorldEvent
        └─ ClientWorld#syncWorldEvent(player, eventId, pos, data)      ← Yarn 名；Mojang ClientLevel#levelEvent(4 参)
             └─ WorldRenderer#processWorldEvent(eventId, pos, data)    ← Mojang LevelRenderer#levelEvent(3 参)
                  ├─ case 1010: item = Item.byRawId(data)
                  │               if (item instanceof MusicDiscItem) playSong(item.getSound(), pos)
                  └─ case 1011: playSong(null, pos)
                       └─ WorldRenderer#playSong(@Nullable SoundEvent song, BlockPos pos)   ← Mojang LevelRenderer#playStreamingMusic
                            · 若该 pos 已有实例 → SoundManager.stop(旧实例) 并从 playingSongs 移除
                            · 若 song != null  → 设置 HUD "现在播放"、new PositionedSoundInstance.record(...)（RECORDS/4.0f/1.0f/LINEAR）
                            ·                      SoundManager.play(实例)、playingSongs.put(pos, 实例)
                            · 无论哪种 → updateEntitiesForSong(...)（鹦鹉跳舞等）
```

**本项目 v0.1 的做法**：Mixin `ClientWorld#syncWorldEvent` 的 HEAD，命中就 `ci.cancel()`。
- 优点：一个点就能决定"归不归我们管"，逻辑最简单；测试重点最少。
- 代价（必须承认）：取消得太早，`WorldRenderer` 那一整套**顺带行为也没执行** → **鹦鹉不会跳舞**、原版自己的 `playingSongs` 记账为空。
- ✅ **其中"HUD 不显示正在播放"已于 0.5.0 还原**：原版那句就是 `inGameHud.setRecordPlayingOverlay(item.getDescription())`，
  而该方法在 1.20.1 是 public 的 —— 所以我们在**真正开声的那一刻**调用同一个方法即可，
  不必移动挂点、也不引入任何 Mixin 风险。唱片名里的备注（`@186016（晴天）`）会作为曲名显示。
- 音频本身不受影响（我们的实例由 `SoundManager` 正常管理，1011 由我们自己的会话收尾）。

**v0.2 建议改成的做法（更贴近原版，保留全部顺带行为）**：把挂点下移到 `WorldRenderer`：

```java
@Mixin(WorldRenderer.class)
public abstract class WorldRendererMixin {
    // 1010：不取消，只把"原版要放的那条实例"换成我们的实例。
    // 这样 HUD、鹦鹉、playingSongs 记账、同 pos 换碟时停旧实例，全都还是原版在管。
    @Redirect(method = "playSong",
              at = @At(value = "INVOKE",
                       target = "Lnet/minecraft/client/sound/SoundManager;play(Lnet/minecraft/client/sound/SoundInstance;)V"))
    private void clouddisc$play(SoundManager manager, SoundInstance vanilla,
                               @Local(argsOnly = true) BlockPos pos) {
        manager.play(pickOursOrDefault(pos, vanilla));
    }

    // 1011：song == null。先收掉我们的实例，再让原版跑完它自己的清理。
    @Inject(method = "playSong", at = @At("HEAD"))
    private void clouddisc$stop(SoundEvent song, BlockPos pos, CallbackInfo ci) {
        if (song == null) stopOursAt(pos);
    }
}
```

Yarn 名已核实：`WorldRenderer#playSong(@Nullable SoundEvent, BlockPos)`、`WorldRenderer#processWorldEvent(int, BlockPos, int)`、私有字段 `playingSongs`（`Map<BlockPos, SoundInstance>`，Mojang `LevelRenderer.playingRecords`）。
依据：[WorldRenderer javadoc](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/client/render/WorldRenderer.html) + `mc1201-decompiled/fjv.java` L2480-2490、L2066-2082。

> **为什么 v0.1 不直接这么写**：`@Local(argsOnly = true)`（Mixin 0.8.3+ 的局部变量捕获）与 `@Redirect` 的组合**只能在真实运行时验证** —— 编译期不会报错，装进游戏才可能因注入失败而报错。工作区里那份反编译源码给了我们确切行号，等你要做 v0.2 时改过去是"照着抄"的工作量，但我不想在一个**无法 `runClient` 验证**的环境里把它当成已经跑通的东西交给你。这一点我在 §15 里也标了"待实测"。

## 4. 播放链路（从右键到出声）

```
玩家A                    服务器                    玩家B / 玩家C
  │  右键唱片机(拿着改名唱片)
  ├── UseBlockCallback（客户端预测）──► PlaybackController.noteLocalUse()
  │      └─ 立刻广播 CLAIM{dim,pos,epoch}  ──────►  记下"这台机器归A管"，
  │                                                  把等待窗口从 6 tick 拉长到 140 tick
  ├── PlayerInteractBlock ──► 服务端插入唱片、开始播放
  │                              │
  │                              ├─ syncWorldEvent 1010 {pos, 物品ID} ──►（所有人）
  │                              │
  ├─ 收到 1010：本机有 pending → 接管                 ├─ 收到 1010：本机无 pending
  │   provider.resolve(trackId)（异步）                │  但 holds 里有 A 的 CLAIM
  │      ↓ 得到 {title, uri}                           │   → 取消原版声音，继续等
  ├─ 广播 PLAY{..., uri, startTick = now + leadTicks} ─► 收到 PLAY
  │                                                     └─ localStartTick = startTick + 时差
  │  各端（含A）在 localStartTick 时刻：下载→解码→seek 到正确位置→预缓冲→play()
  ├─ 之后每秒广播 HB{posMs}  ─────────────────────────► 收到 HB → 偏差>150ms 就 seek 纠偏
  └─ 唱片被取出/播完 → 1011 → 广播 STOP ──────────────► 停止本地会话
```

**几个刻意的设计选择**：

1. **CLAIM 先行**：因为"解析曲目"要联网（可能几百毫秒到几秒），如果等解析完再广播，同伴那边原版唱片声已经响起来了。CLAIM 让同伴**先静音等**。CLAIM 在右键的客户端预测阶段就发出，通常比服务端的 1010 早到（或同刻到）。
2. **没有 CLAIM 时的静音窗口只有 6 tick（300 ms）**：普通（非 CloudDisc）唱片只有 300 ms 延迟，回落逻辑会把原版声音补上。没有同伴（`peerCount()==0`）时**完全不接管**，单人/无同伴场景零干扰。
3. **回落到原版**：等待窗口超时仍没人认领，就用 `MusicDiscItem#getSound()` 通过 `ClientWorld#playSound(...)` 把原版声音补上（会晚 300 ms 起播）。宁可晚一点，也不要一直静音。
4. **统一开始刻**：`startTick = 广播时刻 + startLeadTicks(默认 40 tick = 2 s)`。这 2 秒是给各端下载+预缓冲的预算。

## 5. 音频子系统

### 5.1 数据流

```
文件/HTTP ──► TrackFetcher（落缓存目录） ──► PcmSource（解码，可 seek）
                                              │
                                    AudioPipeline（独立解码线程）
                                      · 多声道 → 单声道
                                      · 线性重采样 → 48 kHz
                                      · 写入 PcmRingBuffer（4 秒容量）
                                              │
                                    PcmAudioStream（MC 音频线程拉取）
                                              │
                                    MC SoundSystem → OpenAL
```

### 5.2 关键决策

| 决策 | 原因 |
|---|---|
| 统一输出 **48 kHz / 16-bit / 单声道** | OpenAL 最稳；**单声道才能被正确空间化**（立体声源通常不会被 3D 定位）。 |
| 解码与音频线程分离 + 环形缓冲 | MC 的音频回调绝不能因为网络/解码卡顿而阻塞。 |
| **欠载时 `getBuffer` 返回 `null`**（不是补静音、不是空缓冲、不是抛异常） | 反编译源码证实：`Channel.pumpBuffers` 里 `null` → **安全跳过这一轮**；空缓冲 → 被当成没数据（可能停掉声音）；抛 `IOException` → 只记日志并**彻底停止 pump**（声音悄悄消失）。所以：`-1` = 真 EOF → 返回空缓冲收尾；`0` = 欠载 → 返回 `null` 让 MC 下一轮再来。 |
| 先落盘再解码（v1） | 换来**样本级 seek**，而 seek 是中途加入与纠偏的前提。边下边播 + Range 放 v2。 |
| 环形缓冲满时解码线程阻塞 | 天然背压，不会把整首歌解进内存。 |
| **开工前先把音频准备好再做 `getStream`** | 因为 RECORDS 音量为 0 时 `SoundSystem.play` 会在调用 `getStream` **之前**就 return。我们把下载/解码/seek 全部放在 `prepareAsync` 阶段，`getStream` 只负责把已经填好的环形缓冲包成 `AudioStream`，于是"玩家音量当时为 0"不会让整条链路失效。 |
| 预缓冲目标 ≈ 1.5 s（可配） | `Channel.attachBufferStream` 会立刻同步 `pumpBuffers(4)`（≈4 秒 PCM）；预缓冲不足时我们返回 `null` 让它下一轮再取，属于安全行为，不会掉歌。想更稳就把 `prebufferMs` 调大（环形缓冲容量 4 s，可一起调）。 |

### 5.3 解码格式选型（含许可影响）

| 格式 | 方案 | 坐标 | License | 说明 |
|---|---|---|---|---|
| **OGG Vorbis** | `org.lwjgl.stb.STBVorbis` | **MC 1.20.1 自带**（LWJGL 3.3.1 含 `lwjgl-stb`） | BSD-3 | **本项目已实现**。零额外依赖、原生库由游戏加载（vanilla 的 `OggAudioStream` 就在用它），支持 `stb_vorbis_seek` 样本级 seek。 |
| **WAV（PCM 16bit）** | 自写 `WavPcmSource`（约 150 行） | 无依赖 | 自己写的，无许可问题 | **本项目已实现**。理由是"零工具就能有测试音频"：音频解码走 Java 读文件，所以中文路径也不会踩 `stb_vorbis_open_filename` 的原生编码坑。只支持未压缩 PCM 16bit，其它位深会明确报错并提示转换命令。 |
| MP3 | `dev.mccue:jlayer` | Maven Central | LGPL-2.1 | JLayer 现代化分支；帧级 seek。LGPL 对分发有额外义务。 |
| FLAC | `org.jflac:jflac-codec:1.5.2` | Maven Central | LGPL-2.1 | 有样本级 seek。 |
| AAC/M4A | `com.tianscar.javasound:jaad:0.9.4` | Maven Central | Apache-2.0 | 若要走 iTunes 试听（`previewUrl` 是 `.m4a`，不是 mp3）。 |

核实来源：[LWJGL STBVorbis javadoc](https://javadoc.lwjgl.org/org/lwjgl/stb/STBVorbis.html)；MC 1.20.1 的 LWJGL 版本与模块见 Prism/Mojang 元数据（`org.lwjgl3:3.3.1`，含 stb + 各平台 natives）。

**v1 建议**：本地曲库一律转成 OGG（`ffmpeg -i in.mp3 -c:a libvorbis -q:a 5 out.ogg`）。理由：零依赖、许可干净、可精确 seek。MP3/FLAC 作为 v0.3 的加分项。

> `AudioFormat` 用 `new AudioFormat(48000f, 16, 1, true, false)`（有符号、小端），与 vanilla `OggAudioStream` 的约定一致。

### 5.4 六个必须知道的坑（全部有反编译源码依据）

1. **音量为 0 → `getStream` 根本不会被调用**：`SoundSystem.play` 里 `if (adjustedVolume == 0 && !shouldAlwaysPlay()) return;`（主音量 ≤ 0 也直接 return）。所以 HTTP/解码**不要放在 `getStream` 里**；本项目把准备工作放在 `getStream` 之前，天然规避。
2. **`getBuffer` 在声音线程被同步调用**：不能阻塞、不能抛。`IOException` 的后果是"只记一条日志然后永远不再 pump"，声音悄悄消失且玩家毫无提示。欠载就返回 `null`。
3. **`getStream` 在 Util 工作线程**：拉流要走自己的线程池并把结果包成 `CompletableFuture`；同时这个 hook **必须 `cancellable`**，否则 vanilla 会真去打开我们那个假 id 并让 future 异常完成。
4. **暂停没有 seek**：窗口失焦/暂停走的是 `alSourcePause`，恢复是 `alSourcePlay` —— 恢复后播放的是暂停前的旧缓冲，会**滞后**一段（等于暂停时长）。要让暂停也精确，需要自己在恢复时重新 seek。
5. **`Sound` 的 id 会被 `new Identifier(...)` 校验字符**（只允许小写 `a-z0-9/._-`），并且 `getLocation()` 会加上 `sounds/` 前缀与 `.ogg` 后缀 —— hook 里必须用"变换后"的 id 匹配，别硬编码。
6. **pos → 实例映射有世界切换问题**：同一 `BlockPos` 在不同维度含义不同，切维度/切服务器时必须清空自己的会话表（本项目在 `ClientPlayConnectionEvents.DISCONNECT` 与 `PlaybackController.shutdown()` 里清）。另外**服务端不会周期性重发 1010**（播放中每 20 tick 发的是 `GameEvent.JUKEBOX_PLAY`，不是 level event），别指望它兜底；重连/换维度后的状态必须靠自己恢复。

## 6. 同步子系统

### 6.1 协议（v1，JSON；UDP 走原文，聊天走 base64）

| 类型 | 方向 | 载荷要点 | 作用 |
|---|---|---|---|
| `CLAIM` | 发起方 → 全体 | dim, pos, epoch | 抢先占位，让同伴静音等待 |
| `PLAY` | 发起方 → 全体 | + prov, track, title, **uri**, durMs, **startTick** | 权威会话开始 |
| `STOP` | 发起方 → 全体 | dim, pos, epoch | 会话结束 |
| `Q` | 任意 → 全体 | dim, pos | "这台机器在放什么？"（迟到玩家/未知唱片） |
| `A` | 会话持有者 → 全体 | 同 PLAY | 对 `Q` 的回答 |
| `HB` | 发起方 → 全体 | epoch, **posMs**, sentTick | 每秒进度心跳，用于纠偏 |

每条消息都带 `sentTick`（发送方本地 `gameTime`）与 `s`（发送者标识），用于 **偏移换算 + 去重 + 忽略自己**。

### 6.2 时间基准：只用"发送方 gameTime"，不搞 NTP

```
接收方：offset = 本地gameTime - msg.sentTick
       localStartTick = msg.startTick + offset
```
- 误差来源只有"发送到接收之间的游戏刻差"（≈ 单向延迟，通常 0–1 tick = 0–50 ms）；
- 不需要额外的时钟同步协议，也不需要假设客户端时钟一致；
- `HB` 每次都重新测量一次 offset，所以偏差不会累积。

> ⚠️ **千万别用错方法（这是会真埋雷的一处）**：Yarn 里
> - `World#getTime()` —— javadoc 原文："Time is used to track scheduled ticks and **cannot be modified or frozen**"，也就是 Mojang 的 `getGameTime()`。**用这个。**
> - `World#getTimeOfDay()` —— 会被 `/time` 命令改、会被 `doDaylightCycle=false` 冻住。拿它当同步基准，别人一 `/time set day` 全服就错位。
> 依据：[World javadoc](https://maven.fabricmc.net/docs/yarn-1.20.1+build.10/net/minecraft/world/World.html)。本项目在 `SyncService` / `PlaybackController` 里统一用 `getTime()`，并在代码注释里写了原因。

### 6.3 对齐与纠偏

各端在 `localStartTick` 时刻开始 `prepareAsync`：
1. 计算此刻应有的**曲内位置** `positionMs = max(0, (now - localStartTick) * 50)`；
2. 下载 → 解码 → `requestSeekBlocking(positionMs)` → 等预缓冲（默认 1.5 s）→ 才调用 `SoundManager.play(instance)`。

> 顺序很重要：**必须等 seek 真正生效再开声**，否则会先冒出 `position=0` 的一小段再跳到目标位置（本项目用 `requestSeekBlocking` + `awaitPrebuffer` 保证）。

播放中，非发起方每秒用 `HB` 校验一次：
```
期望 = hbPosMs + (now - hbAtTick) * 50
实际 = pipeline.playedMs()          // 已交给 OpenAL 的音频时长
若 |期望-实际| > maxDriftMs(默认150) → requestSeek(期望) 硬对齐（有一瞬静音，所以只在偏差明显时做）
```

**关于"漂移"的诚实说明**：真正会累积的漂移极小（音频硬件时钟 vs 系统时钟，ppm 级；一首 3 分钟的歌差几毫秒）。主要误差是**一次性**的：初始 `localStartTick` 精度（±1–2 tick）与 OpenAL 自身缓冲延迟（各端近似相同，属系统性偏差，对"相对同步"无影响）。所以 `HB` 纠偏更多是用来兜住"某端下载慢/中途加入/seek 失败"这类粗差。

### 6.4 中途加入 / 迟到消息

- 迟到玩家进服后：任何 `HB`/`PLAY` 都会让他建会话并按 `positionMs` 对齐（进服时若已过开始刻，`positionMs > 0`，直接 seek 到中间）。
- 主动查询：看到 1010 但没人认领时发 `Q`，会话持有者回 `A`。（`onJoin` 里做一轮主动问答是 v0.2 的增强。）
- `epoch` 用来丢弃**迟到/乱序**的旧消息：同一台唱片机换唱片就是新 epoch。

### 6.5 边界情况（必须在实现里明确处理）

| 情况 | 处理 |
|---|---|
| 原版唱片（没改名）被放进唱片机 | 本机无 pending、无会话 → 无同伴时 PASS；有同伴时静音 6 tick 后**回落原版声音**。 |
| 用漏斗把 CloudDisc 唱片塞进唱片机 | 没有任何客户端"右键"过 → 无 CLAIM/PLAY。同伴会 `Q` 但无人能答 → 各端回落原版。**这是 v1 的已知缺口**，v0.3 用"看物品栏/容器变化反推"补。 |
| 发起方退出游戏 | 其它端已各自持有本地音频，会继续播；只失去 `HB` 纠偏。会话在本地音频播完时自然结束。 |
| 唱片被取出 | 1011 → 广播 STOP → 各端 `instance.dispose()`。 |
| 原版唱片时长用尽 | 服务端到 `MusicDiscItem.getLengthInSeconds()`（例如 cat=185 s、blocks=345 s）就停 → 发 1011 → 我们的会话也结束。**所以能播多久受所选唱片限制**：长曲请用长唱片；或加 `ignoreVanillaStop` 配置由 Mod 按真实音频长度收尾（会与世界状态不同步，默认关闭）。 |
| 同一台电脑开两个客户端 | UDP 需要给两个客户端配不同的 `udpPort`。 |
| 玩家在同一服务器但不在同一局域网 | UDP 广播发现无效 → 需要信令交换公网地址（§7.2）。 |

## 7. 通信层（最需要你做决定的一块）

### 7.1 先说一个必须知道的事实（反编译源码级）

- 客户端发出的 `ServerboundCustomPayloadPacket`（只有 identifier + data，上限 32767 B）到达服务端后，`ServerGamePacketListenerImpl#handleCustomPayload` 是**空方法 `{ }`**：不广播、不回包、不记日志、不踢人。
- **`minecraft:brand` 在 1.20.1 服务端已经不是特例**：该常量只用于服务端→客户端方向（登录时下发 serverModName 供 F3 显示）；服务端源码里没有任何代码读取客户端发来的 brand。
- Paper/Spigot 只在**装了对应插件**时才会把插件消息派发给 `PluginMessageListener`；没有监听器就丢弃，**服务端永远不会自动转发给其他玩家**，要转发必须插件自己 `sendPluginMessage` —— 那需要管理员配合，违背 R1。
- 所以 Fabric/Forge 的 `ServerPlayNetworking` 必须服务端也装 mod（官方文档要求 payload 在 both physical sides 注册）。
- **结论：在 1.20.1，"用插件消息做纯客户端互传"这条路完全不存在。** 唯一原版自带、客户端→全服广播的通道是**聊天**（`/me` 权限等级 0 也能广播；`/say`、`/tellraw` 权限 2 需要 OP；`/msg` 只能定向）。
  依据：`evidence-mc-research/` 里的 1.20.1 反编译源码与 Paper/Forge 补丁。

### 7.2 三条路线

| 方案 | 基础设施 | 延迟 | 被服务器/反作弊针对 | 跨服 | 实现量 |
|---|---|---|---|---|---|
| **A. UDP 点对点 + 局域网广播发现**（主推） | 无（同局域网）；跨公网需一次性信令 | 极低（几十 ms） | 协议外，天然不被针对 | 换服后重新发现即可 | 中（本项目已实现 LAN 部分） |
| **B. 聊天通道**（兜底/信令） | 无 | 中（1–2 tick+，且有限流） | 有风险：限流、日志、聊天管理插件 | 跟着服务器走 | 低 |
| **C. 自建中继服务器** | 一台公网小服务器 | 低 | 无 | 通 | 低（但破坏"零依赖"卖点） |

**推荐组合：A 为主 + B 只做信令/兜底**：
- 同一局域网：A 直接广播发现，零配置。
- 跨公网：用 B 交换一次 `公网IP:端口`（几十字节），然后双方互相往那个地址打 UDP（典型的打洞思路；对称 NAT 下会失败，此时退回 B 传最小同步信息）。
- 也可以给愿意折腾的人一个配置项直接填 `朋友IP:端口`（`UdpTransport.addManualPeer`）。

### 7.3 走聊天通道的真实约束（源码级数字，必须写进 README）

1. **限流是"踢人级"的**：服务端每条广播聊天/命令执行 `chatSpamTickCount += 20`、每 tick −1，累计 **> 200 且非 OP 就 `disconnect("disconnect.spam")`** → **同一窗口第 11 条就把你踢下线**（先广播、再踢）。稳态安全速率 **1 条/秒**，OP 免疫。
   → 本项目因此：心跳间隔从 20 tick 拉长到 **100 tick（5 秒）**，并加了 **0.75 条/秒 + 突发 3 条**的令牌桶，超了就丢消息（宁可少同步一次，也不能把你踢了）。
2. **签名**：`server.properties` 的 `enforce-secure-profile` 在 1.20.1 **默认 true**，服务端用 `SignedMessageChain.Decoder.REJECT_ALL`。
   → 所以**不要自己拼 `ChatMessageC2SPacket`**。本项目走原版客户端自己的发送路径 `ClientPlayNetworkHandler#sendChatMessage(String)`，它会复用客户端当前的聊天签名会话去签名，**发出去是正常已签名消息**。
   → 仍需实测的例外：`enforce-secure-profile=true` 且本机**没有 profile key**（离线登录等）时，客户端聊天会被服务端丢弃并提示 `chat.disabled.missingProfileKey`（红字、不踢人）→ 此时聊天通道**完全不可用**，Mod 必须检测并明确告知玩家，而不是静默不同步。
3. **原版客户端会看到 `[CD1]<base64>` 这样的乱码行**（装 Mod 的客户端由入站 hook 取消渲染）。服务器日志/控制台也会记录（未签名会标 "Not Secure"），聊天管理/反刷屏插件同样读得到 → **歌曲名对管理员可见**。
4. **单条上限 256 字符**，且含非法字符会被 `multiplayer.disconnect.illegal_characters` 踢 → **必须用 Base64/hex 等可打印 ASCII**。因为长度限制，聊天通道**不携带 URL**（`Protocol.packForChat` 会剥掉 `uri`）；此时对端必须自己能解析同一个短 key。
5. 结论：聊天只适合**低频、非敏感**的会话事件与信令；主数据通道交给 UDP。

> 骨架里 `ChatTransport` 的**出站已实现**（含令牌桶限流），入站 hook 留了唯一的接缝 `ChatTransport.ingest(String)`。1.20.1 的入站聊天有三个分支（`ClientPlayNetworkHandler#onChatMessage` / `onProfilelessChatMessage` / system chat），或用 fabric-message-api-v1 的 `ClientReceiveMessageEvents.ALLOW_CHAT/ALLOW_GAME` 统一拦截并取消渲染。**这是骨架里唯一刻意留空的地方** —— 它必须实机验证，我不想给你一个"看起来接了其实没接上"的东西。

### 7.4 顺便一提：局域网发现可以更强

原版自己的 LAN 发现用的是 **UDP 组播 `224.0.2.60:4445`**（`LanServerPinger`，每 1.5 s 一条）。本项目当前用广播（255.255.255.255 + 各网卡子网广播 + 环回）；v0.2 可以并行加一条组播（另开一个端口，避免和原版 LAN 公告混在一起），在"广播被交换机/防火墙挡住但组播能通"的网络里更稳。

跨公网打洞的现实成功率也要有预期：RFC 5128 的口径是"**>80% 的 NAT 可以打洞，但只有 EIM 型 NAT 行，对称 NAT 必失败，必须准备 relay 兜底**"；Tailscale 的工程经验是 >90% 能直连、其余走中继。所以跨公网这条路的正确姿势是：**打洞为主 + 失败自动退回聊天通道/中继**。
（对比参考：**Simple Voice Chat / Plasmo Voice 都必须服务端也装**，因为它们要做端口与密钥交换、还要服务端当中继；真实存在的 1.20.1 音乐 mod **AudioPlayer** 干脆放弃 MC 音频引擎、改用 Simple Voice Chat 自建声道 —— 这也说明本项目"真正替换唱片机声音"的路线比现成方案更激进。）

## 8. 曲目识别与音源 provider

### 8.1 名字格式与解析权

```
@186016                     ← 最简：@ + 网易云歌曲 id
@186016（晴天）              ← 备注可选；播放时显示的真名是联网查回来的，备注拼在真名后面
@186016 晴天 / @186016-晴天   ← 备注用别的分隔符也行（只认开头那串数字）
@https://music.163.com/song?id=186016   ← 直接粘分享链接
@local:晴天                  ← 显式走本地文件 clouddisc-music/晴天.ogg
@163:186016 / @netease: / @wy:          ← 显式音源（别名）仍然可用
```
- **解析只在发起方做一次**，结果（`title` + `uri`）随 `PLAY` 广播 → 别人不需要账号、不需要 API、不需要配音源。
- **显示用的曲名是联网查回来的真名**（0.6.0 起）：唱片名里只存歌曲 id，
  播放时查"歌名 - 歌手"显示在屏幕下方（`InGameHud#setRecordPlayingOverlay`，与原版同一处行为，见 §2.4）。
  查询与音频地址解析并行、1.2 秒预算、**三级兜底**（`/api/song/detail/?id=X&ids=[X]` →
  `/api/song/detail?ids=[X]` → 网页 `og:title`），全部实测过；
  三级都失败就回退到"玩家备注 → `网易云 #id`"，**绝不影响播放**。
  请求带 UA/Referer，但**不带任何账号或 cookie**。
- 解析失败 → 不发 `PLAY`；同伴的等待窗口超时后回落原版（用户能直观看到"没生效"，不会静默卡住）。
- 铁砧输入框上限 50 字符：`@` + 最多 12 位 id + 约 35 字备注。
- 两个容易写错的细节：
  1. **URL 里自带 `:`**，所以 `DiscName.parse` 对"以 http(s)/file 开头"的名字**不按 `:` 切音源**；
  2. 更一般地，只有"冒号前确实是**已注册的音源名**"才按 `<音源>:<曲目>` 解析，否则这个冒号算备注的一部分（例如 `@186016（晴天: 现场版）`）。

### 8.1.1 网易云：实测过的可用范围（这一节是实测，不是推测）

对外链 `https://music.163.com/song/media/outer/url?id=<id>.mp3` 抽样 8 首（2026-10）：

| 曲目类型 | 实测结果 | 能否播 |
|---|---|---|
| 免费 / 非独家 | `200 + audio/mpeg`，302 → `http://m80x.music.126.net/....mp3`（3–5 MB） | ✅ |
| VIP / 独家 / 下架 / 地区受限 | 302 → `https://music.163.com/404`，`text/html`（107 KB） | ❌ |

三条由此得出的实现要求：

1. **HTTP 客户端必须允许 https→http 的重定向跟随**。外链的 302 目标是 **http** 的 CDN 地址，
   而 Java `HttpClient.Redirect.NORMAL` 的语义是"除 https→http 外都跟随" → curl 能拿到音频、Java 会停在 302 上。
   本项目用 `Redirect.ALWAYS`（音频非机密数据，跟随降级是合理的）。
2. **必须校验 `Content-Type`**：VIP 曲目返回的是 `HTTP 200 + text/html`（不是 4xx！），
   不拦的话只会得到一个语焉不详的"解码失败"。本项目在 `TrackFetcher` 里明确报出
   "拿到的是 text/html（107191 字节的网页），不是音频文件"，并提示去配 `neteaseEndpoint`。
3. **UA / Referer 无关**（用 mod 自己的 UA 也能拿到音频，实测三种 UA 一致），所以不需要任何伪装头。

结论：这条链路**只播"匿名就能播的内容"**。要放 VIP 曲目，只能由玩家提供自己的解析服务
（`neteaseEndpoint`），这既是技术现实，也是我做合规边界的地方。

### 8.2 合规与安全（这条我会明确坚持）

- **不内置任何账号、cookie 或加签逻辑。** 网易云 provider 只做"识别分享链接/歌曲 id → 展开成一条音频地址"：
  默认模板是网易自己的**公开外链**（一个可以在配置里换掉的公开 URL，不是接口调用，也不带任何凭据）；
  配了 `neteaseEndpoint` 就优先走玩家自己的服务。**登录态永远只在玩家本机。**
- **不绕过付费/DRM**：实测也证明网易对 VIP/独家曲目直接返回 404 网页——本 Mod 拿到就明确报错，不做任何规避尝试。
- **不支持 `.ncm` 等加密/受保护格式的解密**，也不做"解锁灰色歌曲"这类绕过。
- **不缓存后再分发**：缓存只为本机播放，且受 `cacheMaxMb` 限制。
- 背景（供你判断风险，已核实）：`Binaryify/NeteaseCloudMusicApi` 仓库已 `archived`、代码清空、`license` 字段为 `null`；GitLab 镜像 404；作者留话"保护版权，此仓库不再维护"（[仓库 API](https://api.github.com/repos/Binaryify/NeteaseCloudMusicApi)、[IT之家 2024-01-24 报道](https://www.ithome.com/0/746/942.htm)）。**把这条链路做成产品级内置功能，风险不只是技术问题。**
- 默认音源用 **本地文件**；想联机的建议 **自建 Subsonic/Navidrome/Jellyfin**（`stream` 端点，天然支持 Range）。
**安全（很实际的一点）**：`PLAY` 里的 `uri` 来自别的玩家，客户端会去下载它 → 这是典型的 SSRF/欺负人面。本项目的策略按**来源可信度**分三档（`TrackFetcher.Trust`）：

| 来源 | 策略 |
|---|---|
| `SELF`：本机自己的 provider 解析出来的（例如你配的 `neteaseEndpoint` 跑在 `127.0.0.1`） | 只校验协议——**自建本地音源必须能用**，否则这条最轻量的方案就被自己封死了 |
| `PEER_ALLOW_PRIVATE`（默认）：别的玩家给的地址，允许私网 | 为了"同一局域网的自建 Navidrome/Jellyfin 也能被同伴播放"；仍然拒绝环回/链路本地/云元数据地址 |
| `PEER_BLOCK_PRIVATE`：想更严就切这个 | 连私网也拒绝 |

另外还有：只允许 http/https、限制体积（`maxTrackMb`）与超时、请求不带任何本机凭据、`Content-Type` 校验。
**域名白名单**建议加配置项进一步收窄（v0.2）。

### 9.2 纯客户端分发语义（回答"需不需要服务器装"）

- `fabric.mod.json` 里 `"environment": "client"`：**只影响本地加载**，专用服务端根本不加载这个 mod；它不是"要求服务器也装"。Fabric 也**没有服务端 mod 列表校验** → 装客户端即可连任意原版服务器，服务器不会因此拒绝。
  依据：[fabric.mod.json 规范](https://wiki.fabricmc.net/documentation:fabric_mod_json_spec)
- 三件套要齐：`environment: client` + `entrypoints.client` + `mixins` 里带 `"environment": "client"` 的配置块；客户端专属类建议再加 `@Environment(EnvType.CLIENT)`。

### 9.3 Mixin 要点

- **refmap 由 Loom 自动生成**，不要手写混淆名；开发期就写 Yarn 名。
  依据：[Loom 文档](https://docs.fabricmc.net/develop/loom/)
- `compatibilityLevel` 用 `JAVA_17`。
- 方法名可用简写（`method = "loadStreamed"`）——只要不重载；重载必须写描述符。
- 本项目两个注入点：
  - `SoundLoader#loadStreamed(Identifier, boolean)` —— `@At("HEAD")` + `cancellable`，替换流；
  - `ClientWorld#syncWorldEvent(PlayerEntity, int, BlockPos, int)` —— 世界事件 1010/1011 的接管判定。
- 调 `MinecraftClient.getInstance().execute(...)` 把后台线程的动作切回客户端线程（`play/stop` 必须在线程上做）。

### 9.4 本机实测记录（你可以复核）

- 环境：Windows，PATH 上只有 JDK 8；用启动器自带的 `%APPDATA%\.minecraft\runtime\java-runtime-gamma-snapshot`（**17.0.15，含 javac**）当 `JAVA_HOME`，Gradle 8.8。
- `gradle build` 首次约 8 分钟（下载 MC + 各平台依赖 + 重映射），之后增量 3–20 秒。最终产物 `clouddisc-0.1.0.jar`。
- **编译过程抓出的 4 类真错（都是"看文档看不出、编译器才知道"的）**：
  1. `net.minecraft.client.sound.AudioStream` **继承 `Closeable`**，必须实现 `close()` —— javadoc 的"成员列表"不显示继承方法，所以只能靠编译器告诉你。
  2. `World#getGameTime()` **不是** Yarn 名，Yarn 叫 **`getTime()`**（而 `getTimeOfDay()` 是另一个会被 `/time` 改的钟，差点用错，见 §6.2）。
  3. `ClientPlayerEntity` 上**没有** `sendChatMessage(String)`；发聊天要在 **`ClientPlayNetworkHandler#sendChatMessage(String)`**。
  4. 我自己定义的 record 组件名是 `durationMsHint`，调用处写成 `durationMs()` —— 记录一下，提醒"记录组件名就是访问器名"。
- 结论：**"以为读懂了 API" 和 "真的编译过" 是两件事**。这也是我坚持给你一个能编译的骨架、而不是一段伪代码的原因；同时也要提醒：Mixin 的注入是否成功**编译期查不出来**，那必须 `runClient`（§15.2）。

## 10. 失败模式与降级

| 失败 | 用户可见表现 | 设计上的处理 |
|---|---|---|
| 解析失败（key 写错/接口没配/文件不存在） | 唱片机不出声（或晚 300 ms 出原版声） | 不发 PLAY；日志给出原因；HUD 提示（v0.2） |
| 下载失败/超时 | 该玩家听不到，其它玩家正常 | 该会话标记 DEAD，不阻塞别人；重试按钮（v0.2） |
| 预缓冲超时 | 起播晚一点（按已过时间 seek 对齐） | `awaitPrebuffer` 超时后照样 `play()`，并用 `HB` 追齐 |
| 无对端（单人/同伴没装/网络不通） | 完全不影响原版行为 | `peerCount()==0` → 一律 PASS |
| 聊天通道被限流/被拒 | 仅失去兜底同步 | UDP 主通道仍在；日志告警 |
| 原版时长用尽 | 音乐被服务端截断 | 用长唱片；或 `ignoreVanillaStop`（默认关） |
| 音频欠载（网络抖动） | 一小段静音/杂音，**不掉歌** | 环形缓冲 + 欠载补静音（§5.2） |

## 12. 测试方案

**必须实测的清单（按优先级）**

1. `SoundLoader#loadStreamed` 的注入是否生效：放一张 CloudDisc 唱片，原版唱片声**必须完全没有**（不是"被盖住"，是根本不出声）。
2. `Sound` 的 `getLocation()` 变换后的 `Identifier` 长什么样：日志打一行，确认 `StreamRegistry.normalize` 命中（这是最容易挂的地方）。
3. 音量滑块（"唱片机/音符盒"那一档）、主音量、暂停（Esc）、窗口失焦：我们的声音必须跟着变/停。
4. 唱片取出（1011）、唱片机被破坏：声音必须干净停止，`StreamRegistry.size()` 归零，无残留 OpenAL source。
5. 双端同步：同一台唱片机，两端 `HB` 纠偏日志里的偏差应长期 <150 ms。
6. 欠载鲁棒性：播放中断网 3 秒，声音不应戛然而止（应为静音后恢复）。
7. 反例：**不装 Mod 的另一台客户端**能正常进服、能正常听原版唱片（我们的静音窗口只有 300 ms 且会回落）。
8. 聊天通道：`[CD1]...` 行**不会**出现在装了 Mod 的客户端聊天框里。

## 14. 风险清单

| 风险 | 等级 | 说明与缓解 |
|---|---|---|
| 音频注入点行为与预期不符 | 中 | 已在 javadoc 层核实到方法级；仍需实测 `getLocation()` 变换与流生命周期。**先用日志确认再写复杂逻辑。** |
| 聊天通道被服务器拒绝/限流 | 中 | 只做兜底；主通道 UDP；失败要**明确告诉玩家**而不是静默不同步。 |
| 跨公网 UDP 打洞失败（对称 NAT） | 中 | 退聊天通道；或让玩家填 `朋友IP:端口`；或自建中继。 |
| 版权/ToS（把平台音频接进第三方客户端） | **高** | 见 §8.2：不内置接口、不内置凭据、不支持解密受保护格式、不缓存再分发；把它做成"玩家自备音源"。 |
| 别的玩家的 URL 带来的 SSRF/大文件 | 中 | 已做协议/私网/体积/超时限制；再补域名白名单。 |
| 原版唱片时长限制 | 低 | 用长唱片；可选 `ignoreVanillaStop`。 |
| 与原版/其它 mod 冲突 | 低 | 只动了 2 个方法；未接管非 CloudDisc 唱片；`client` 环境不加载到服务端。 |

## 15. 已核实 vs 待实测

### 15.1 已核实到源码/字节码级（可以当事实用）

- 原版服务端 `handleCustomPayload` 是空方法、`minecraft:brand` 服务端不读 → 插件消息**不可能**用于纯客户端互传。
- 聊天限流阈值（`+= 20` / tick −1 / `> 200` 踢 = 窗口第 11 条）、`enforce-secure-profile` 默认 true 与 `REJECT_ALL`、单条 256 字符、非法字符会踢。
- `SoundSystem.play` 的流式分支确实走 `soundBuffers.getStream(sound.getLocation(), shouldRepeatInstantly)`；`getStream` **无缓存**；`getBuffer` 在声音线程调用，`null` = 安全跳过、`IOException` = 停止 pump。
- `JukeboxBlockEntity` 不覆写 update-packet（NBT 键为 `RecordItem`/`IsPlaying`/`RecordStartTick`/`TickCount`）；1010 的 data = `Item.getId(item)`，1011 的 data = **0**；无 BlockEntityRenderer。
- `World.getTime()` = 单调、不可修改/冻结的游戏刻；`getTimeOfDay()` 会被 `/time` 与 `doDaylightCycle` 影响。
- `SoundLoader#loadStreamed` 是取流入口；`Sound#getLocation()` 会做 `sounds/<path>.ogg` 变换；`WeightedSoundSet` 可绕过 `sounds.json`；`Sound` 构造器 public。
- 音频引擎线程模型：`getStream` 在 Util 工作线程、`getBuffer` 在 SoundExecutor 线程、`SoundManager.play` 内部 `createHandle(...).join()` 会短暂阻塞。

### 15.2 待实测（编译期查不出来，必须 `runClient`）

1. **两个 Mixin 在真实运行时的注入**（`loadStreamed` / `syncWorldEvent`），以及 `StreamRegistry` 的 id 归一化能否命中真实的 `getLocation()` 结果 → **第一步就加日志把它打出来**。
2. 音频听感：起播对齐精度、纠偏是否平滑（seek 会有一瞬静音）、暂停/失焦恢复后的滞后。
3. 聊天通道的入站 hook 选哪个分支（§7.3），以及"取消渲染"是否干净。
4. `enforce-secure-profile=true` 且无 profile key 时的实际表现。
5. 原版唱片播完后唱片是否弹出（只影响文案）。
6. 铁砧输入框 50 字符上限（影响可编码的信息量）。
7. 双端/三端同步的实测偏差分布（目标：长期 <150 ms）。
