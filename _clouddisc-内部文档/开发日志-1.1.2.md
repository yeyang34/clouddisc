## 1. 物理声效：按「穿过了几道门」算闷度

**现象（用户原话）**：「我家两室一厅，进门是客厅。外面放歌我在客厅，隔一个门道，清亮——这没错。但我进次级房间，隔了客厅门道 + 大门门道，理应闷一些，结果还是清亮。」

**根因**：旧判据只看**通不通**，不看**穿了几道门**。

- `floodAir()` 一次把整片连通空气并成**一个**距离场 ⇒ 大门、客厅、卧室在算法眼里是同一间房。
- 拿到距离后一句 `f = min(0.02 + 0.35*detour, 0.15)` —— **0.15 的硬顶让绕行距离彻底失效**：绕 2 格是 0.15，绕 60 格翻过屋顶再翻回来还是 0.15。
- 另有三道"往清亮方向兜底"的钳制（`openPaths>=3 → 0.05`、`edgePaths → 0.45`、`backPaths → 0.25`）和一句 `occ = occMain * pow(fracBlocked, 1.5)`。

**改动**：`audio/Acoustics.java`

| 新增/改动 | 作用 |
|---|---|
| `airPath()` | 带 parent 表的 **A\***，求"唱片机 → 耳朵"的空气最短路径（旧的纯 BFS 见第 11 条） |
| `countDoorways()` / `isDoorwayCell()` | 沿路径数**窄颈** = 门道 |
| `portalCountOfRun()` | 短窄颈算 1 道，≥4 格的窄走廊算 2 道（两端各一个开口） |
| `cachedAirPath()` | 5 刻缓存，避免每帧重算 |
| 落地 | `occ = 0.15 + 0.20 × (N−1)`，N 封顶 3，遮挡封顶 0.85，与材质遮挡取 min |

**门道的三条判据**（全几何，不预设户型）：

1. 只统计**横向一步**（竖直移动不算 ⇒ "从墙顶上方翻过去"不会误判成门）
2. 垂直于行进方向的水平宽度 ≤ `physicsDoorwayMaxWidth`（默认 2 格）
3. 该列头顶净空 ≤ 2 格（门/走廊 2 格高；露天往上没有上限 ⇒ 不算门）

**验证**：把判据 1:1 照抄成脚本（`doorway-sim2.ps1`），6 个合成场景全过：

```
two rooms / 2 doors        expect=2  got=2
outside -> living          expect=1  got=1
one wall + sky above       expect=0  got=0    ← 回归项
sealed room               expect=-1 got=-1    ← 走材质遮挡
living+corridor+bed        expect=3  got=3
one open door block        expect=1  got=1
```

脚本跑的过程中抓出两个真 bug：① 验证网格把地板铺在人脚上；② **长窄走廊被并成一道门** ⇒ 才补了 `portalCountOfRun`。

**实机验收**：用户确认「效果不错」（门道模型通过）。

**回退**：`physicsDoorwayModel = false` ⇒ 完全回到 1.1.1 的旧逻辑（旧分支一行没删，只是被 `!doorModel` 门控）。

## 4. 选歌界面「收藏」

**为什么单独存文件**：收藏必须**与搜索无关** —— 断网、解析服务挂了、只想快速找到常听的歌，都得能列出来。所以把显示需要的字段（名字/歌手/专辑/时长/类型/原始 key）一起存下来，打开界面**不发任何请求**。

- 存储：`music/Favorites.java` → `config/clouddisc-favorites.json`（纯本地、纯客户端）
- 交互：行首 ☆/★（点星只切换收藏，**不选中不确认**，防手滑改掉唱片名）+ `F` 键
- 上限 500 条，新的在最前

**主键设计（踩过的坑）**：一开始用"裸数字 id"，后来 B 站进来（`BV` 号是字符串）就必须统一：

- 两边都有数字 id ⇒ **只比 id**（同一首歌从"单曲"或"历史"进来都是同一条）
- 否则比字符串 key（B 站）

`isFav()` 是**每帧 × 每行**调用的，所以里面**绝不能拼字符串**（500 条 × 60 帧会造大量垃圾），先比 `long` 再比字符串。

## 5. 选歌界面「历史」（含别人放的）

**关键设计：打点位置**。不记"点了确认"，而是记 `PlaybackController` 里**真正开声**那一刻：

```java
Minecraft.getInstance().getSoundManager().play(instance);
s.state = JukeboxSession.State.PLAYING;
// ← 历史记录打点在这里
```

好处：

- 本机发起和**别人放的**走同一处（多人里别人放唱片，你收到同步、本地开声，那一刻进你的历史）
- 解析失败 / 没音频 / 被人拔碟的**从来走不到这一句**，所以历史里不会有坏条目
- `JukeboxSession.historyLogged` 保证 seek/重连不会记重复

**去重**：同一首重放不新增条目，提到最前 + 次数 +1（否则单曲循环一会儿就刷满）。上限 200 条。

**key 一致性坑**：唱片名只写 `@BV…` 时 `session.provider` 是空的（靠 trackId 自动识别），若直接把空 provider 写进 key，历史里是 `:BV…`、收藏里是 `bili:BV…` ⇒ 同一首歌"历史里星星不亮" ✗。所以 `History.record` 会**补一次音源推断**。

## 6. 选歌界面「B站」

### 6.1 可行性验证（先做，再写代码）

在用户服务器（Ubuntu 24.04）上实测：

| 测试 | 结果 |
|---|---|
| `/x/web-interface/view` | ✅ 不需要 cookie |
| `/x/player/playurl` | ✅ **连 wbi 签名都不需要**，`code=0` |
| 音频档位 | 30216(64k) / 30232(132k) / **30280(192k)**，匿名就拿到 192k |
| 音频直链 | ❌ **不带 Referer 直接 403** |

> 注：本机（非服务器）裸请求返回 `{"code":-352}`（风控）。同一套请求在用户服务器上正常 —— 说明 `-352` 是 IP/头指纹问题，不是接口变了。

### 6.2 服务端（`_serverside/resolver.py`，已部署）

新增两条路由：

| 路由 | 作用 |
|---|---|
| `GET /bili?url=<链接或BV/av号>&p=N` | 返回标题 / UP主 / 时长 / **所有分P** / 取流地址 |
| `GET /bili/stream/{BV}?p=N&token=…` | 现场解析直链 → **ffmpeg 转 mp3** → 缓存 → 分发（支持 Range） |

**为什么必须转码**：B 站只给 AAC（MP4 容器，`ftypiso5`），而 mod 的解码器只有 `Mp3PcmSource` / `OggPcmSource` / `WavPcmSource` / flac ⇒ `detectFormat()` 会判成 `unknown` **直接播不了**。

**实测证据**：

```
全量下载     → 5,097,230 B，magic=49 44 33（ID3），Content-Type: audio/mpeg
二次请求     → 0 秒（命中缓存）
多P(4P)     → 正确展开 P1~P4，时长 229/225/225/225 秒
P2 转码     → 7 秒，5,383,500 B，ffprobe 实测 224.28s（接口报 225s）
完整URL+?p=2 → 单P视频自动收敛到 p1
垃圾输入     → {"error":"bili resolve failed: no bvid/aid in input"}
```

**防"撑爆服务器"的四道限制**（用户明确要求）：

| 限制 | 值（环境变量） | 效果 |
|---|---|---|
| 并发转码 | 2（`CDR_BILI_CONCURRENCY`） | 第 3 个排队，30 秒排不上直接拒绝 |
| ffmpeg 线程 + 优先级 | `-threads 2` + `nice -n 10` | 宁可慢，不抢别的服务 |
| 单首输出 | 120MB（`CDR_BILI_MAX_OUT_MB`） | 超了删文件并报错 |
| 视频时长 | 3600s（`CDR_BILI_MAX_SEC`） | 转码前就拒绝 |
| 缓存总量 | 300MB（`CDR_BILI_CACHE_MB`） | 按最久未用 LRU 清理 |

压测实测（3 个请求同时打同一首）：服务常驻 **13.6MB**、ffmpeg 峰值 **56MB**、整机峰值已用 **632MB**（总 1613MB）、load **0.28**、结束后 0 个残留 ffmpeg 进程、缓存目录 11MB。

### 6.3 客户端

- `music/BiliProvider.java`（id `bili`）：`BV…` ⇄ `/bili?bvid=&p=`；**基址默认复用网易云那台服务**（`biliEndpoint` 留空即可）
- `music/BiliSearch.java`：界面用，解析出 `List<Item>`，多P 展开成多行
- 注册进 `Providers`，`DiscName` 的 `@<provider>:<trackId>` 机制直接支持

### 6.4 名字格式（用户指定）

| | 格式 |
|---|---|
| 单P | `@BV1xx411c7mD` |
| 分P | `@BV1xx411c7mD#p3` |

**为什么不能用数字**：网易云的自动识别规则是 `LEADING_ID = ^\s*(\d{1,12})(?!\d)` —— **以数字开头即歌曲 id**，任何纯数字的 B 站标识都会跟网易云撞车。`BV` 开头在网易云那条永远不成立 ⇒ 天然不冲突 ✓

**路由顺序**也相应调整：`startSession()` 里 **BV 优先于网易云**判断。`@bili:BV…` 这种显式写法仍然认（provider 已注册），不会坏。

## 8. 单曲缓存 64→96MB、缓存总量 512→768MB

**起因**：B 站转 192kbps mp3，**约 44 分钟就到 64MB**，而服务端允许 60 分钟（约 86MB）⇒ 客户端的 `maxTrackMb` 会**先**拒掉。

- `maxTrackMb` 64 → **96**（≈ 68 分钟 192kbps，正好盖住服务端那条限制）
- `cacheMaxMb` 512 → **768**（不然两三首长视频就把缓存挤爆）

**迁移**（`configVersion` 8）：只在这两个值**恰好还是旧默认**时才改，避免覆盖用户自己调过的值：

```java
if (configVersion < 8) {
    if (maxTrackMb == 64) maxTrackMb = 96;
    if (cacheMaxMb == 512) cacheMaxMb = 768;
}
```

## 9.5 播放前的状态提示（借用「正在播放」那行）

**动机（用户提出）**：解析 / 转码 / 下载 / 预缓冲这段时间是**静默**的，唱片机其实在干活，
但玩家会以为"按了没反应"。

**为什么能借用**：屏幕下方那行本来是原版显示「正在播放: xxx」的，
本质是"一条带倒计时的文本"，**反复写就能一直挂着** ⇒ 播放前这几十秒可以拿它当状态行。

**实现**：`gui/HudStatus.java`（薄封装 + 全 try/catch）＋ `PlaybackController` 三处打点：

| 阶段 | 显示 | 数字从哪来 |
|---|---|---|
| 解析中 | `☁ <id> · 正在解析…` | 一次性 |
| B 站首次 | `☁ <名> · 服务器转码中…（首次约 5~10 秒）` | 这段客户端**一个字节都收不到**，只能定性说明 |
| 下载中 | `☁ <名> · 缓冲中 3.2 MB · 480 KB/s` | 读 `.part` 文件大小 + 自采样速率（**真实值**） |
| 已排好起点 | `☁ <名> · 即将开始 1.2 秒` | 由 `localStartTick` 换算（**真倒计时**） |
| 播放 | 原来的曲名（不变） | — |

**关键取舍：不编数字。** 下载总量（Content-Length）当前拿不到，
所以不显示百分比/剩余秒数，只显示"已收多少 + 多快"；而"即将开始"那段的倒计时是真的。

**没碰下载代码**：进度靠只读 `.part` 文件大小（`TrackFetcher.partBytes`），
下载主流程一行没改 —— 这块是全 mod 最不能出错的路径，不值得为一行提示去动它。

**已知待验**：原版那行是否对"反复写"友好（会不会只在开头显示一次）。若实机发现只闪一下就消失，
备选方案是改用动作栏（`player.displayClientMessage(comp, true)`）。

## 10. 修复多人模式下「时长解锁」失效

**现象**：单人正常；**服务端也装了本 mod 时失效**。

**根因有两层，同一个功能被两条路废掉**：

1. **`fabric.mod.json` 里 `"environment": "client"`** ⇒ 整份 mixin 配置在专用服务端**根本不加载**，`JukeboxLibMixin` 与字段访问器都不存在，服务端就是纯原版唱片机。
   （`clouddisc.mixins.json` 自己已经分好 `mixins` / `client` 两段 ⇒ 这个字段纯属多余且有害）
2. 即使注入了也会失效：`clouddisc$isOurDisc()` 里日志走的是**客户端类** `CloudDiscClient`，服务端一抛异常就被同一个 `try` 的 `catch` 吞成 `return false` ⇒ 每张云唱片都被判成"不是我们的碟"。

**改动**：

- 删掉 `fabric.mod.json` 的 `"environment": "client"`
- `JukeboxLibMixin` 改用 slf4j 自取 logger（**不再碰任何客户端类**），并**先算结果、后打日志**

**验证口径**：服务端控制台应出现

```
[CloudDisc] 时长解锁判断: 唱片名=@123456 是否云唱片=true
[CloudDisc] 时长解锁: 已到 N 刻，云唱片计数归零继续播放 ✓
```

**这两行以前在服务端不可能出现** —— 出现了就说明修好了。

⚠ **服务端必须换同一个 jar**。当前状态：客户端已换，**服务端 jar 尚未更新**（用户主动搁置）。

### 验收记录（2026-10-20 20:47，本地专用 Fabric 服务端）

搭了一台本地服务端验证（`default-workspace\mcserver-26.2`，`online-mode=false`、创造、25565），
服务端 mods 只放 `fabric-api` + `clouddisc-1.1.2.jar`。**实测通过**，证据三条：

```
[Mixin Subsystem] ... Env=SERVER
[WARN] Redundant @Unique on injector method clouddisc$probeTick(...) in JukeboxLibMixin from mod clouddisc
[CloudDisc] 服务端同步中继已就绪：频道 clouddisc:relay

[20:47:32] [Server thread/INFO]: [CloudDisc] 时长解锁判断: 唱片名=@BV17Lan6vE5c#p30 是否云唱片=true
[20:47:32] [Server thread/INFO]: [CloudDisc] 时长解锁: 已到 1940 刻，云唱片计数归零继续播放 ✓
```

要点：

- 第一行证明 mixin 在 **`Env=SERVER`** 下被应用（修复前 `environment: client` 时它连解析都不做）
- `[Server thread]` 是专用服务端线程，**不可能来自客户端**

## 11. 修复室外被一根柱子挡住视线就闷

**现象**：1.1.2 内测阶段，室外隔着柱子/树就闷，连"不做门道模型"的旧行为都不如。

**根因（我自己引入的回归）**：第 1 条把"求空气路径"从 `roomPathLength` 的双向泛洪换成了**单次纯 BFS**，还沿用 8000 格探索上限。但纯 BFS 在开阔地形按**球面**铺开：

> 8000 格 ≈ 半径 12 格的球。

⇒ 十几二十格外就"走不到"听者 ⇒ 返回"空气不通" ⇒ `occDoor = -1` ⇒ 又因为我关掉了旧的"通就不闷"兜底 ⇒ 直接吃满材质遮挡。

**为什么旧的没这问题**：双向泛洪两端各铺 12 格，**只要两个球重叠就算通**（能撑到 ~24 格）。但它拿不到路径、数不出门道 —— 我把能力换掉了，却没把"够得着"补上。

**改动**：`airPath()` 改成 **A\***（曼哈顿启发，6 邻域单步代价 1 ⇒ 可采纳且一致），朝听者直奔；查询距离 48 → 64 格；`maxExpanded` 6000 兜底。

另加**回归保险**：找不到路径时（超距/迷宫/超探索上限）**旧的"≥3 条偏移射线通透 ⇒ 压到 0.05"重新生效** ⇒ "室外一根柱子"在任何情况下都不可能再变闷。

**证据**（同一张真正开阔的三维地图）：

| 距离 | 纯 BFS（旧） | A\*（新） |
|---|---|---|
| 8~20 格 | 正常 | 正常 |
| **30 格** | **-1（判成不通）** | 30 ✓ |
| **45 格** | **-1（判成不通）** | 45 ✓ |

顺带补回一个会丢的 1.1.1 修复：**"人站在屋顶上"**那条（无路径时仍按主射线遮挡），否则会被新兜底重新判成通透。

## 已知限制（都跟 B 站相关）

1. **只能播正常投稿视频**。番剧 / 付费课程 / 直播拿不到纯音频，会报 `no dash audio`。
2. **历史不回溯**：别人在你不在线时放的歌，协议里没有回放，不会补进历史。要跨会话记录得改协议、让服务端存。
3. **首次播放要等转码**（约 7 秒/首），之后走缓存零等待。
4. 服务端缓存上限 300MB，超出按最久未用清理 —— 热门长视频可能被清掉再转一次。
