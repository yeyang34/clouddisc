## 一、26.2 的网络形态（与 1.20.1 完全不同 ✗）

| 1.20.1（我们原来用的） | 26.2 |
|---|---|
| `net.minecraft.network.PacketByteBuf` | `net.minecraft.network.FriendlyByteBuf` ✓（已有 ✓） |
| `ClientPlayNetworking.registerGlobalReceiver(Identifier, (client, handler, buf, sender) -> …)` | `registerGlobalReceiver(CustomPacketPayload.Type<T>, ClientPlayNetworking.PlayPayloadHandler<T>)` ✓ |
| `ClientPlayNetworking.send(Identifier, PacketByteBuf)` | `send(CustomPacketPayload)` ✓ |
| 无类型概念 ✗ | 必须定义 `CustomPacketPayload` 实现 + `Type` + `StreamCodec` ✓ |

## 装机规矩（重要 ✓ 血泪教训）

**装 jar 前必须先关掉游戏** ✗ —— 否则会出现下面这种极难排查的错误：
```
java.util.zip.ZipException: ZipFile invalid LOC header (bad signature)
```
它长得像"我们的类加载失败"✗ 其实是 **jar 被写了一半** ✗（游戏正读着这个文件 ✓ 我们同时覆盖它 ✓）。

本仓库的装机流程（agent 用 ✓）：
1. 构建 → **逐条目读一遍产物**（坏 zip 立刻暴露 ✓）
2. 复制到 mods 里的 `xxx.tmp` → **再逐条目读一遍** ✓
3. 校验通过后**原子替换**成正式的 `.jar`（先删旧 ✓ 再 Move ✓）
4. 替换后**再读一遍 + 比对 SHA256**（两边必须一致 ✓）
5. 如果检测到 java 进程在跑 ✗ → 提示使用者关闭游戏后再装 ✓
## 两个已踩过的自动化坑（务必避免 ✗）

1. **不许再无条件提交** ✗
   有一次我在"构建失败"的情况下照样执行了 commit ✗ → 把坏代码提交了 ✗ →
   之后 `git checkout -- <file>` 只会恢复到【坏版本】✗ 我一度以为恢复失灵 ✗
   **规则**：先构建 ✓ 只有 BUILD SUCCESSFUL 才 commit ✓ 否则只改不提交 ✓

2. **PowerShell 里给 git 提交消息时不要带引号** ✗
   `git commit -m "… "从开头放" …"` → 路径解析炸掉 ✗（pathspec 错误 ✗）
   **规则**：提交消息里一律用「」或不用引号 ✓ 或者用单引号包整条消息 ✓

3. **行范围替换要先确认范围** ✗
   有几次我按"若干行"替换，结果把后面的方法头一起删了 ✗ → 结构报错 ✗
   **规则**：替换前先打印目标范围前后各 5 行 ✓ 确认边界 ✓ 替换后再打印核对 ✓
